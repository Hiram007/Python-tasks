Design system

Design prototype, not a replacement system. The existing Django application remains the production system of record. This prototype exists to agree the interface and the workflow states before they are implemented in Python, and it never calls Base44 services at runtime.

Hiding a control in the interface is never a security control

Authorisation must be enforced by the Django backend on every request

Simulated in this prototype

Works in the browser, but nothing is stored, sent or enforced.

Not implemented
  • No persistence. Every form, approval, completion and clearance is held in the page and lost on reload.
  • No authentication. The role switcher changes what is shown; there is no sign-in, session or identity check.
  • No authorisation. Approval buttons and restricted panels are hidden or shown by role for review only.
  • No email or notifications. Reminders, digests and delivery history are described, never sent.
  • No Microsoft 365 or Entra ID. SSO, MFA, group mapping and provisioning are shown as unconfigured.
  • No file storage. Document and evidence uploads are represented by empty states.
  • No scheduling. Due-date reminders, overdue escalations and weekly summaries are not scheduled.
  • No exports. Export controls explain the permission and confidentiality rules; no file is generated.
  • No audit writes. Audit entries illustrate the intended record, but no event is stored.
  • No database. The prototype has no database, cache or queue of any kind.

Real and working in the prototype

Behaviour the Django implementation must reproduce exactly.

Working here
  • Table filtering, sorting tabs and empty states across every list screen.
  • Form validation with inline errors, an error summary and accessible error wiring.
  • Checklist progress arithmetic — section and case-level progress derived from the rendered rows.
  • Confirmation dialogs for approvals, rejections, returns, destructive actions and guarded actions.
  • Mandatory comments on rejection, return and administrative change decisions.
  • Guard rules — a case cannot be marked ready while tasks are open, and clearance cannot be recorded while actions and assets are outstanding.
  • Role-based visibility of navigation, dashboard panels and restricted information panels.
  • Responsive layout from wide desktop down to tablet and phone, with tables stacking and the sidebar becoming a drawer.
  • Accessibility basics — skip link, visible labels, focus handling, aria-current, status text beside every status colour.

Preview and implementation notes

Where the prototype lives, how to hand it over, and how it maps onto Django.

Preview

The running prototype on port 3000, live-reloading as files change

Source

The prototype/ directory of this repository — plain HTML, CSS and vanilla JavaScript

Handover options

Copy the folder into the Django project as templates and static files, or open a pull request to review it before merging

Runtime dependency on Base44

None — no SDK, no backend call and no external request anywhere in the prototype

Local dev server

prototype/server.py — standard library only; expands include comments and reloads on change

Automated tests

None in this repository; the prototype was verified by hand and with browser automation

Template inheritance

Each page currently repeats the shell around a single include. That maps one-to-one onto a Django base template, so the conversion is mechanical:

{% comment %} prototype/partials/sidebar.html becomes one include {% endcomment %} {% extends "a_d/base.html" %} {% block title %}Departure cases{% endblock %} {% block body_class %}app{% endblock %} {% block content %} {% include "partials/sidebar.html" %} {# role-gated navigation groups #} {% include "partials/topbar.html" %} {# role switcher becomes the signed-in user #} {% for case in departure_cases %} {% include "partials/case_row.html" with case=case %} {% empty %} {% include "partials/empty_state.html" with noun="departure cases" %} {% endfor %} {% endblock %}

Implementation order that keeps the production system safe

Port the design system first (tokens and components as static files), then the read-only screens (dashboard, directory, case lists and case files, reports), then replace the prototype's show-and-tell interactions with real POST endpoints one journey at a time. Every screen in this prototype is a rendering of data the Django application already owns; nothing here requires a new data model to be invented.

Verification: every page renders, navigation matches the role, and the core journeys were exercised in a browser
