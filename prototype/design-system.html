Brand

The product mark is a two-arrow glyph: arrivals and departures. It sits on the indigo brand gradient in the sidebar.

Casidra

Arrivals & Departures

The wordmark is always paired with the product name Arrivals & Departures in the sidebar, and used alone where space is tight.

Product language

  • Arrivals — new starters. Cases, checklists, day-one readiness.
  • Departures — leavers. Reserved for the offboarding module, which reuses every component here.
  • Department — HR, IT, Facilities or Communications: the owner of a checklist.
  • Coordinator — the person accountable for a case end to end.

Conventions

  • Landmarks — one main, a labelled nav for sidebar and breadcrumbs, and a skip link before them.
  • Colour is never the only signal — status badges carry a word, progress bars carry a percentage, due dates carry an icon plus text.
  • Focus — 2px brand outline on :focus-visible; the mobile drawer returns focus to its trigger.
  • Forms — visible labels, aria-invalid, aria-describedby error text and an role="alert" summary.
  • Live regions — the toast stack is aria-live="polite"; dialogs are native dialog elements with aria-labelledby.
  • Tables — caption, column scope, and restacked rows that keep their labels on small screens.
  • Motion — all transitions are disabled under prefers-reduced-motion.
  • Targets — interactive controls are at least 32px, most are 38px or taller.

Mapping to Django templates

The prototype is deliberately plain HTML and CSS so it can be lifted into an existing Django project without a build step.

Prototype markup mapped to Django template structure
PrototypeDjango templateNotes
assets/css/tokens.css static/css/tokens.css Ship as static files; keep the variable names so both products stay in sync.
partials/sidebar.html + topbar.html base.html + {% include %} One base template with {% block content %}; the active nav item comes from a context variable instead of the JSON data-page attribute.
partials/icons.html partials/_icons.html Included once per document, before the sidebar.
.kpi / .badge / .progress partials/_kpi.html, _status_badge.html Pass label, value, delta and tone through the include context — the tone maps to badge--ok, --warn, --danger or --info.
Case table rows {% for case in cases %}{% include "partials/_case_row.html" %} Filter values become GET parameters; the data-table-* attributes can stay for client-side filtering or be replaced by server-side queries.
Checklist sections {% for section in checklist_sections %} … _checklist_section.html Each section needs department, owner, done count and its tasks. The department modifier classes (dept--hr …) map to a dict on the section.
Task row partials/_task_row.html Task status drives the badge tone and whether approval buttons render.
Timeline / steps partials/_timeline_item.html Milestone class comes from a state field: done, active, blocked, upcoming.
Dialogs, sheets, toasts base.html (once) + form views Keep the generic confirmation dialog in the base template; Django form errors can render the same .field.has-error markup.
Offboarding Reuse every partial above Only the vocabulary changes: exits instead of starts, clearance tasks instead of onboarding tasks. The shell, tables, checklists, timeline and dialogs are unchanged.

What this prototype does not do

There is no backend, no authentication, no permissions model, no persistence and no email delivery. Every approval, completion and form submission here changes the page in the browser only.
